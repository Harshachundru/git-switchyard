Switchyard

Multi-Profile Routing Guide

Running a personal account, a work account, and maybe a GitLab account off one machine means every push needs to land on the right track. This is the order you check, wire, and test it in.

Format · one page, eleven sidings Shell · bash / zsh Keys · ed25519
01

Check which track you're on

Run these before you push, especially in a folder you didn't clone yourself. The third command is the one that actually explains a wrong identity — it shows which file set it.

CommandWhat it does
git remote -vShow the remote URL(s) this repo pushes to — and which host/account they point at
git config user.nameShow the name that will be attached to commits made here
git config user.emailShow the email that will be attached to commits made here
git config --show-origin --show-scope user.emailShow which config file (local repo, global, or system) set that email
02

Lay a new key

One key per identity. Give each a name when prompted (or with -f) so you never overwrite an existing one.

CommandWhat it does
ssh-keygen -t ed25519 -C "you@example.com" -f ~/.ssh/id_ed25519_personalGenerate a new ed25519 key pair for one identity, saved under its own filename
chmod 600 ~/.ssh/id_ed25519_personalLock the private key down to your user only — SSH refuses keys that are too open
03

Copy the public half

Only the .pub file ever leaves your machine — paste it into GitHub/GitLab under Settings → SSH Keys. Never share or upload the private key.

CommandWhat it does
pbcopy < ~/.ssh/id_ed25519_personal.pubCopy the public key to the clipboard (macOS)
xclip -selection clipboard < ~/.ssh/id_ed25519_personal.pubCopy the public key to the clipboard (Linux)
clip < ~/.ssh/id_ed25519_personal.pubCopy the public key to the clipboard (Windows, Git Bash)
cat ~/.ssh/id_ed25519_personal.pubJust print it, if you'd rather select and copy by hand
04

Wire the switchboard

Edit ~/.ssh/config (create it if it doesn't exist) and give every non-default identity its own Host alias. The alias is what routes traffic to the right key — SSH otherwise has no way to tell your accounts apart.

# Default GitHub account
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

# Personal GitHub account
Host github.com-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_personal
    IdentitiesOnly yes

# GitLab account
Host gitlab.com
    HostName gitlab.com
    User git
    IdentityFile ~/.ssh/id_ed25519_gitlab
    IdentitiesOnly yes

Then lock the file down the same way as the keys:

chmod 600 ~/.ssh/configRestrict the config file to your user only
05

Test every siding

Confirms SSH is picking the right key before you push anything. A working line answers with "Hi <username>! You've successfully authenticated…".

CommandWhat it does
ssh -T git@github.com-personalTest the personal GitHub alias
ssh -T git@github.comTest the default GitHub identity
ssh -T git@gitlab.comTest the GitLab identity
ssh-add -lList every key currently loaded into the SSH agent
06

Route a new clone

Whenever you start a new repo under a non-default account, clone through that account's alias and set the identity locally — never globally, or it'll leak into every other repo.

CommandWhat it does
git clone git@github.com-personal:<username>/<repo>.gitClone using the personal alias, so pushes route through the personal key
git remote set-url origin git@github.com-personal:<username>/<repo>.gitRepoint an already-cloned repo's remote at the correct alias
git config --local user.name "<Your Name>"Set the commit name for this repo only
git config --local user.email "<you@example.com>"Set the commit email for this repo only
07

Automate it by folder

Setting user.name/user.email by hand in every new repo is exactly the step people forget. includeIf in ~/.gitconfig switches identity automatically based on where the repo lives on disk — no per-repo command needed.

[includeIf "gitdir:~/personal/"]
    path = ~/.gitconfig-personal

[includeIf "gitdir:~/work/"]
    path = ~/.gitconfig-work

Each of those points at a small file holding just the identity for that folder:

# ~/.gitconfig-personal
[user]
    name = <Your Name>
    email = <you@example.com>
08

Keep the agent loaded

On macOS, the agent forgets keys on reboot unless you tell Keychain to hold them — do this once per key, and never retype a passphrase again.

CommandWhat it does
ssh-add --apple-use-keychain ~/.ssh/id_ed25519_personalLoad the key into the agent and remember it in macOS Keychain (macOS)
eval "$(ssh-agent -s)"Start an SSH agent for the current shell session (Linux)
ssh-add ~/.ssh/id_ed25519_personalLoad a key into the running agent (Linux)
09

Send the first train

Everything above assumes the repo already exists. A brand-new folder has no track at all until git init, and no destination until you add a remote. Do it in this order, and address the remote through your account's alias (github.com-personal) — a plain git@github.com address quietly routes through your default key instead.

First, create the destination on GitHub as an empty repo — no README, no .gitignore, no licence. Anything GitHub adds on creation is history your local repo doesn't have, and it will bounce your first push.

CommandWhat it does
git init -b mainTurn the current folder into a repo with main as its first branch (-b needs a value)
git branch -M mainRename the current branch to main if the repo already started life as master
git config --show-origin user.emailCheck the identity now that it's a repo — see siding 11 for why this matters
git add . && git commit -m "Initial commit"Stage everything and make the first commit
git remote add origin git@github.com-personal:<username>/<repo>.gitName the destination origin, using the personal alias so the personal key is offered
git remote -vRead the remote back — confirm the host says github.com-personal, not github.com, and that the repo name is spelled right
git push -u origin mainSend the branch and remember it, so later a bare git push knows where to go
10

Read the derailment

When a push fails, the error names the exact cause of the wreck — you only have to know which fault it points at. The four you are most likely to meet on a first push are the first four rows. Most come down to one of three things: you are not standing in a repo, the remote address is wrong, or the remote has history you don't.

Error you seeWhat it means, and the fix
fatal: not a git repository (or any of the parent directories): .gitYou are outside a repo, so every git remote and git push fails. cd into the project, or run git init -b main if it was never initialised. git rev-parse --show-toplevel shows which repo you are in
git@github.com: Permission denied (publickey).SSH offered a key GitHub doesn't accept for this account — almost always because the remote uses the plain github.com host instead of your alias. Compare git remote -v with your Host lines, then git remote set-url origin git@github.com-personal:<username>/<repo>.git. If it persists, ssh -vT git@github.com-personal shows which key is being offered
ERROR: Repository not found.The repo doesn't exist under that account, the name or username is misspelled, or the key belongs to an account with no access. Create the empty repo on GitHub, or correct the URL with git remote set-url
! [rejected] main -> main (fetch first)The remote already holds commits you don't have — usually a README added at creation. If that history is unwanted, delete and recreate the repo empty. To keep it: git pull origin main --allow-unrelated-histories, then push again
fatal: refusing to merge unrelated historiesA pull met two histories with no common ancestor. Add --allow-unrelated-histories once, deliberately, as in the row above
error: remote origin already exists.Don't add it again — repoint it: git remote set-url origin <new-url>
error: No such remote 'origin'The opposite mistake: there is nothing to repoint yet. Use git remote add origin <url> first
fatal: The current branch main has no upstream branch.First push of a branch. Run git push -u origin main once; plain git push works afterwards
head: #: No such file or directoryNot a git error — you pasted a command with a trailing # comment into zsh, which doesn't treat # as a comment at an interactive prompt, so the comment words were passed as arguments. Drop the comment, or run setopt interactivecomments once (add it to ~/.zshrc to keep it)
error: switch `b' requires a valueThe branch name is missing: git init -b main, not git init -b

A typo in a remote name doesn't error at all — it just creates a second, useless remote (orogin next to a missing origin). That is why git remote -v belongs after every change:

git remote rename orogin originFix a misspelled remote name in place
git remote remove oroginDelete a stray remote you added by mistake
git remote set-url origin git@github.com-personal:<username>/<repo>.gitSwitch an https://… remote to SSH — HTTPS never uses your SSH keys at all, so the alias only helps once the URL is SSH
11

Check the conductor's badge

The push can succeed and still be wrong: the key decides where the train is allowed to go, but the commit's author badge decides who is recorded as driving it. If your global identity is your work account, a commit made in a personal folder carries the work name and email — and it is now stamped into history. Look at the badge before the first push, when fixing it is free.

One trap: includeIf "gitdir:…" from siding 07 only applies inside a repo. Running git config user.email in a folder that hasn't been git init-ed shows your global identity no matter how well the rules are written. Check after git init, not before.

CommandWhat it does
git log -1 --format='%an <%ae>'Show the author name and email recorded on the latest commit
git log --format='%h %an <%ae>'List the author on every commit, to see how far the wrong badge spread
git config --local user.name "<Your Name>"Set the correct name for this repo only
git config --local user.email "<you@example.com>"Set the correct email for this repo only — the GitHub …@users.noreply.github.com address keeps your real one private
git commit --amend --reset-author --no-editRe-stamp the latest commit with the identity now configured, keeping its message
git rebase -r --root --exec "git commit --amend --no-edit --reset-author"Re-stamp every commit when there is more than one. Rewrites history — only do this before anything has been pushed or shared

Once a wrong-author commit has been pushed, the fix means force-pushing rewritten history, which breaks anyone who already pulled it. Cheaper to never get there: verify the badge with the first command above, every time, before a first push.

Before you publish or share a key

  • Commit only .pub files anywhere, ever — a private key belongs on one machine, in ~/.ssh, mode 600
  • Add config to your global ~/.ssh — never to a repo's .gitignore as if that were protection; it should never be inside a repo at all
  • Run git log -1 --format='%an <%ae>' before a first push — a wrong author is free to fix locally and expensive to fix once it is on the remote
  • If a private key is ever pushed by accident, treat it as compromised: revoke it on the remote host and generate a fresh one — rewriting history does not undo the exposure
